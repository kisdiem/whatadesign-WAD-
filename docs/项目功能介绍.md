## 一、项目概述

**一句话定位**：从 TB 级多源安全日志（Syslog / ETW / WAF / DNS）中，用**无监督 / 弱监督**方法识别**罕见攻击链**与异常模式，并**有效降低人工研判成本**。

**核心叙事**：系统不是普通 SIEM 仪表盘，而是围绕 **Finding（发现）→ Investigation（案件）→ Evidence（证据）→ Analyst Decision（分析员决策）** 的调查工作流构建。

**三套演示数据集（同一套前端消费逻辑，按数据集语义区分）**：

| 数据集 | 事件数 | 时间跨度 | 语义 | 用途 |
|---|---:|---|---|---|
| Short | 2,749 | 30 分钟 | 短程突发 | 快速检查页面与证据追溯，短程基准链 4 步 |
| Long | 44,775 | 7 天 | 长程 | 长时间范围、攻击链与全量日志检索，长程基准链 10 步 |
| APT | 7,298 | 7 天 | 完整 APT 叙事 | 10 分钟演示主数据集，10 步 ATT&CK 攻击链，跨 6 类日志源 / 4 台主机 / 3 个账户 |

合计约 **5.5 万条**受控事件流（Long 的 88% 为真实网络遥测采样，见 7.3）。

**核心演示数字（7 天视角）**：

- 原始事件约 **5.5 万** 条（Short 2,749 + Long 44,775 + APT 7,298）
- Short/Long 异常发现收敛到 **1,239** 条候选；其中**系统自动处置 1,211** 条（40 条自动处置链 + 自动归档）→ 进入人工研判 **28** 条 → 研判压缩率 **99.941%**
- APT 数据集 30 条异常（medium 13 / high 15 / critical 2），10 步基准链 `APT-CANDIDATE-001` 待人工研判，链罕见度 73%
- 待研判案件以**自由拼装链**呈现：已确认主链窗口按时间先后构成单向链，候选证据（真证据 + 干扰项混合）作为灰色独立节点在下方自由池待研判；分析员拖拽候选到主链任意位置（首/中/尾）补入，或拖到排除区直接排除，形成"候选池 → 自由拼装 → 闭环"的研判过程
- 链路长度按数据集语义区分：Short 短程基准链 4 步、Long 长程基准链 10 步、APT 基准链 10 步；自动处置链 Short ≤5 成员、Long/APT ≤10 成员，长程链明显长于短程

**为什么这么做**：真实攻击往往只有几十条，淹没在海量日志里，靠人逐条看不过来。系统的价值不是"画得好看"，而是把"海量日志 → 少量需要人看的候选证据"这条闭环跑通，并且每一步都可解释、可追溯。

## 二、三项核心创新

| 创新 | 一句话说明 | 对应模块 |
|---|---|---|
| 面向当前事件的多尺度上下文主动检索 | 不以等量扫描全部历史，而是以当前异常事件为锚点，在 1h/24h/7d/30d 四个尺度上按需扩展检索 | M4 |
| 跨时间窗口的长周期攻击链关联 | 用强弱锚点 + 时间衰减关联跨窗口、跨日攻击链，恢复短窗口检测看不到的完整攻击链 | M5 |
| 跨源日志语义统一与实体关系联合建模 | 把 Syslog/EVTX/WAF/DNS 统一到同一事件语义与实体空间，构建事件—实体异构关系图 | M1/M2/M3 |

**为什么是这三项**：这是评委最可能问的三个"你们和别人有什么不同"的点。演示剧本（`docs/演示剧本_10分钟_APT版.md`）以一个新增的 APT 数据集为主线，用"攻击者 7 天跨 6 类日志、4 台主机，最后被还原成 10 步攻击链"的逻辑自洽故事，逐页对应落地这三个创新——总览页讲"多尺度"，案件页讲"长周期链"，发现/实体页讲"跨源语义统一"。

## 三、整体架构

```
前端 (React + Vite + TypeScript + Ant Design + ECharts)  http://127.0.0.1:5173
后端 (Python FastAPI + Uvicorn)                          http://127.0.0.1:8000
数据层
  ├─ 可追溯回放：frontend/public/demo-data/{Short,Long,APT}
  ├─ 实时小文件：FastAPI → M0-M6 原型链路 → SQLite (run_state/wad_ingestion.db)
  ├─ 前端领域层：Finding / Investigation / Evidence / EntityProfile
  ├─ 后端服务层：agent_service（小影、日志与实体查询接口）
  └─ 原始素材层：AIT-ADS / AIT-LDSv2 / EVTX 等数据集
```

前后端通过 `/api` 代理联通（Vite dev proxy 指向 `127.0.0.1:8000`）。

**两层数据路径，为什么要分**：

- **可追溯回放层**（默认加载）：Short/Long/APT 三套带真实源时间戳和原始日志文本的回放包，保证演示任何时间、任何网络环境都可用，且完整保留"原始日志 → 结论"的可追溯性。其中 APT 是专为 10 分钟演示剧本设计的完整攻击叙事集（详见 7.3）。
- **实时接入层**：数据源页上传真实小文件，走后端完整 M0-M6 链路 + SQLite 持久化，证明系统不是前端假数据。

## 四、检测链路M0-M6

### 4.1 各阶段职责

| 阶段 | 执行内容 | 代码位置 |
|---|---|---|
| M0 | Drain 模板解析、原始引用和解析置信度 | `src/parsers/`、`agent_service/ingestion.py` |
| M1 | 语义标准化、行为/结果识别、无标签弱监督规则信号 | `src/semantic/` |
| M2 | 用户、主机、IP、进程实体提取、规范化和文件内稀有度 | `src/entities/` |
| M3 | 实体图上下文、关系数量和新颖度 | `src/graph/` |
| M4 | 无监督模板稀有度、失败上下文异常分数 | `src/models/` |
| M5 | 共享实体的较早风险事件关联（长周期攻击链） | `src/temporal/` |
| M6 | M1-M5 可解释加权融合，生成风险发现与候选案件 | `src/fusion/` |

### 4.2 M6 融合公式（全链路一致）

```
M6 = clamp(0.30*M1 + 0.12*M2 + 0.14*M3 + 0.28*M4 + 0.16*M5)
```

**为什么权重是这样**：M1 弱监督信号（0.30）和 M4 模板稀有度（0.28）权重最高——因为它们最直接刻画"这个事件像不像攻击"（规则命中）和"这个模板在日志里多罕见"（稀有度）；M2/M3/M5 作为辅助信号补充实体与上下文维度。**关键**：演示回放数据与实时上传链路用**同一套公式和规则**，避免两套算法不一致被评委质疑。

### 4.3 弱监督规则（M1 信号源）

规则来自 `agent_service/ingestion.py` / `scripts/m6_calibration/_scoring.py`：

| 命中关键词 | M1 弱监督分 |
|---|---|
| mimikatz / lsass | 0.88 |
| powershell -enc / certutil / rundll32 | 0.82 |
| useradd / new user | 0.78 |
| failed password / 4625 | 0.72 |
| sudo 提权 | 0.68 |
| denied / WAF 告警 | 0.64 |
| dns / connect 异常 | 0.60 |
| 默认（普通日志） | 0.08 |

**为什么用弱监督而不是强监督**：真实场景缺乏大规模干净标注，用少量高置信关键词规则（如 mimikatz 必然可疑）即可获得有区分度的先验，且天然可解释——每个分数都能说出"为什么"。

### 4.4 评分细节（上传链路）

- **M2 实体稀有度**：`entity_rarity = 1/sqrt(出现次数)`，`m2 = 0.2 + 0.55*rarity`（实体越罕见分越高）
- **M3 图上下文**：`m3 = 0.12 + min(实体数,5)*0.09 + 多实体奖励0.20`
- **M4 模板稀有度**：`template_rarity = 1/sqrt(模板出现次数)`，失败上下文 +0.22
- **M5 长程关联**：与过去最多 100 条风险事件按共享实体关联，`m5 = 0.12 + min(linked,3)*0.22 + 强信号加成0.18`

**为什么"稀有度"反复出现**：攻击者的武器（账户、主机、进程、日志模板）在目标网络里天然少见，稀有度是无需标签就能捕捉异常的核心信号。但稀有 ≠ 恶意——UI 上处处强调这一点，避免误报被当成结论。

## 五、前端功能详解

### 5.0 主工作台（MissionControlApp.tsx）

前端入口，负责所有页面的数据组装与全局状态。

**功能点**：

- **左侧导航栏（8 页）**：总览 / 发现 / 实体调查 / 案件调查 / 日志检索 / 数据源 / 小影 / 评测，路由级懒加载。
- **侧边栏健康状态**：检测服务运行中、日志源在线数、证据状态库——给评委"系统在实时工作"的直观信号。
- **顶部时间范围选择器**：过去 1 小时 / 24 小时 / 7 天 / 30 天，全局生效，是"多尺度上下文"的交互入口。
- **自动刷新开关**：定时刷新真实上传数据。
- **小影悬浮窗（AssistantDock）**：右下角悬浮、可拖拽调整位置、可收起。**为什么**：用户切换页面时小影会话不中断，悬浮窗在后台继续运行——这是"操作助手"而非"对话框"的产品定位。
- **数据组装**：加载 Short/Long/APT 三套回放包 + 实时上传数据（`getIngestionSnapshot`），合并成窗口、案件、事件流、总览序列；本地加载失败时回退到后端 API，再失败则明确报错（**不再隐式回退静态 Mock**）。
- **localStorage 持久化**：案件列表（`wad-demo-case-items-v5`）、案件分层（`wad-demo-case-boards-v4`）、M3 图快照、图拖拽坐标、已删除案件——刷新页面后调查状态不丢。
- **上下文感知的小影启动**：从案件/实体/发现进入小影时，自动注入对应上下文并触发首轮起手分析（`buildAssistantKickoff`）。
- **可执行动作（assistantActions）**：根据当前上下文生成"查看案件 / 打开实体 / 查看发现 / 检索日志"按钮，点一下自动跳转对应页面并继续对话。

### 5.1 总览页（OverviewPage）

**页面定位**：全局态势入口，回答"当前窗口有多少日志、多少异常、收敛到多少人工研判"。

**区块与功能**：

1. **统计卡（4 张）**：原始事件数、异常发现数、进入人工研判数、研判压缩率。为什么：开篇用四个数字讲"研判压缩"这个故事。
2. **研判漏斗**：左侧五层收敛列表（L1 事件 → L2 异常发现 → **L3 系统自动处置**（自动处置链 + 自动归档）→ L4 进入人工研判 → L5 主链证据），右侧 ECharts 折线（原始事件）+ 柱状（异常发现）双系列图。为什么：可视化"海量 → 少量"的漏斗式收敛，并明确展示**绝大多数异常无需人工**——系统自动处置层（`demoData.ts` 的 `buildAutomaticResolutions`）把未进入案件的窗口按共享实体 + 24h 时间窗聚成 `queueStatus=resolved`、归属"系统自动研判"的自动处置链，孤立低危窗口自动归档，只有少数高风险链进入人工研判。
3. **跨域来源分布双层环图**：外环（主）= 日志文件类型（网络遥测 / 系统日志 / 认证日志 / Windows 事件 EVTX / DNS 隧道 / 审计日志 / 入侵检测），内环（辅）= Short/Long/APT 数据集分类，中心标注"原始事件"。为什么：既保留数据集分类，又用文件类型体现"跨域采集"能力（APT 数据集的 Suricata / DNS 扇区天然体现跨源，EVTX 与 DNS 扇区另见 7.6 的注入样本）；口径是**原始事件**而非异常——避免被单一类型霸屏。
4. **高风险发现**：按综合风险降序前 5 条，同时展示综合分与长程分。
5. **分析链路**：M0→M6 七张静态卡片，讲方法链路。
6. **筛选联动**：右上角"全部日志源"下拉联动统计卡、漏斗、环图、高风险列表；时间范围按源分组各自截断（`filterRowsBySourceTimeRange`），保证每个源的时间口径独立。**为什么**：切换时间范围时，Short（30 分钟内完成）和 Long（跨 7 天）的对比必须各自正确。

**数据来源**：全部由主工作台 props 注入（demo 回放序列 + 实时上传序列 + 领域层加工结果）。

### 5.2 发现页（FindingsPage）

**页面定位**：模型候选异常的复核队列，回答"先看哪条"。

**区块与功能**：

- **筛选/排序工具栏**：关键词搜索、风险等级下拉、日志源下拉、四种排序（综合风险 / 长程关联 / 事件异常 / 发现时间）。
- **发现列表**：标题+ID、实体及类型、综合风险徽章、**三层分数**（事件异常 eventScore / 局部上下文 localScore / 长程关联 longScore，进度条渲染）、理由标签。
- **详情抽屉**：
  - 调查锚点：异常发现 ID、实体、主机、锚点事件、Investigation Range（1 小时）、Model Context（30 分钟）
  - **M6 风险融合**：四个分数卡 + weak_fusion_v2 说明（36% 事件 + 29% 局部 + 35% 长程）
  - **远程候选**：长程关联的候选证据列表
  - **M5 关联依据**：关联置信度、共享锚点、锚点强度、实体稀有度、行为兼容度、图相似度、时间间隔
  - 证据：陈述句 + 原始日志引用
  - 可执行按钮：保存 30 分钟 M3 关联图 / 跳实体画像 / 跳案件 / 交给小影
- **为什么三层分数分开展示**：综合风险是融合输出，不是黑盒结论——三层分开才能回答评委"这分数怎么来的"；远程候选强调"候选 ≠ 结论"的证据边界。

**数据来源**：`buildFindings` / `buildEvidence`（领域层）加工 AnomalyWindow 而成。

### 5.3 实体调查页（EntityInvestigationPage）

**页面定位**：以单个实体（用户/主机/进程/IP/资产）为中心的 30 天画像与基线偏离分析。

**区块与功能**：

- **实体列表（左栏）**：搜索、实体 ID/类型/最近活动/异常关系数标签，支持 `?entity=` 直达。
- **实体头部卡**：名称（双击交给小影解释）、类型、首末出现时间、关注级别（高关注/需核查/一般关注）、自动生成的实体说明。
- **统计卡（4 张）**：时间范围内事件、正常主机数、当前主机数、新增关系数。
- **基线对比表**：特征（Event Count / 来源多样性 / 当前主机 / 稀有度）、当前观察 vs 历史常态、偏离进度条（≥0.8 明显偏离 / ≥0.6 有所偏离）。
- **关联发现表**：与该实体相关的 Finding 及可点击的关联理由。
- **调查提示卡**：三条静态复核建议。
- **批量提交小影**：把当前筛选的全部实体序列化后一次性交给小影归纳。
- **真实数据模式**：非 mock 且未强制 demo 时，并行请求后端 `getSecurityEntity` / `getSecurityEntityHistory` / `getSecurityBaseline` 三个接口派生画像。
- **为什么**：这是"稀有性 ≠ 恶意"观念的载体——锚点分析看的是**偏离基线**，而不是单点稀有。

**数据来源**：本地模式为 `buildEntityProfiles` 产物；真实模式为后端实体三接口 + fallback。

### 5.4 案件调查页（InvestigationsPage，最复杂）

**页面定位**：攻击链核验工作台，把 Finding 按案件聚类，支持人工把证据分为**主链 / 候选 / 排除**三段，并可视化 ATT&CK 技术链与 M3 事件图。

**区块与功能**：

- **链路队列（左栏）**：两级筛选——数据集（全部/Short/Long/APT/其他）+ 队列状态（待研判/**自动处置**/完成/全部）；支持 `?case=` 直达。
- **系统自动处置链**：未进入任何案件的异常窗口由 `buildAutomaticResolutions`（共享实体 + 24h 时间窗聚类，链长上限 10、行为族多样性护栏避免巨型链）聚成自动处置链（`id` 形如 `SHORT-DISP-001`，`queueStatus=resolved`、`decisionSource=system`、owner="系统自动研判"），落在队列"自动处置"分类；未成链的孤立低危窗口自动归档（计入总览漏斗 L3）。自动处置链同样支持查看 ATT&CK 攻击链图、主链/候选/排除三段管理，并可一键**升级人工案件**。为什么：绝大多数异常系统已自动研判处置，只有少量高风险链需要人工复核，把"11 条待研判"之外的一千多条也展示出来。队列分类规则见 `shared.tsx` 的 `isSystemResolved`（resolved 且决策来源为 system → 自动处置；resolved 且 analyst → 完成）。
- **案件头卡**：标题、owner、队列状态、升级评分、方法标签（多尺度主动检索 / 长周期关联 / 跨源语义）、升级原因、锚点实体。
- **攻击链路研判图（自由拼装链）**：已确认主链窗口按 `windowIds` 顺序从左到右构成单向链（超出画布自动换行），相邻窗口以节点边缘端口连线衔接、方向箭头表示时间先后；红色实心为已确认主链，下方灰色虚线为候选证据自由池（`gapEvidenceIds` 真证据 + `gapDistractorIds` 干扰项混合）。**拖拽候选证据**到主链任意节点前后即可按位置补入 `windowIds`（绿色「＋」指示落点，插首/中间/尾均可），节点随即转为红色主线并自动重排；拖到右上角「拖到此处排除」区直接排除。可点卡右上角「小影」，由 小影 基于当前主链与候选池给出还原顺序建议与排除项，辅助人工判断。系统不给候选排序，由分析员亲手决定它属于链条哪一段或直接剔除。基准链（`*-CANDIDATE-*`）同样只保留已确认窗口，保证待研判队列案件形态一致。
- **自动攻击链提取**：攻击链图上方展示系统**自动提取**的完整链路（`services/autoAttackChain.ts`）——把案件内异常事件按 ATT&CK 战术阶段聚合，渲染为**分步链路卡片**（每张卡片：战术序号/战术名 → 技术 ID → 证据数 → 首条证据时间），并输出**阶段覆盖数**与**链级罕见度**，同时与人工基准链阶段数对照。实测对比：Short 基准链 30 分钟内完成 7 阶段、罕见度 60%；Long 基准链跨度 7 天、罕见度 47%——"短时间内完成整条链更罕见"的特征自然呈现；APT 基准链跨度 7 天、罕见度 73%、覆盖 7 个战术阶段（初始访问 → 执行 → 持久化 → 权限提升 → 凭证访问 → 发现 → 命令与控制）。与人工整理的基准链并存供对照，并带边界声明（自动链是调查投影，需人工确认）。
  - **罕见度数据来源**：`链罕见度 = 35%·M2实体稀有 + 30%·M4模板稀有 + 20%·时间压缩度 + 15%·高风险占比`。其中 M2/M4 是**真实数据标定**（占 65% 权重）：两者都是 `project_m6.py` 基于四源 2.2 亿行真实日志扫描的 `baseline.json` 频率统计（高频实体/模板降权 `0.5+0.5/(1+log₁₀(freq+1))`）算出的**事件级分数**，本模块只做"按案件聚合求平均"；时间压缩度（20%）是**可解释的领域启发式**（短时间走完整条链更异常，公式 `1-log₁₀(跨度+1)/3` 透明可复现）；高风险占比（15%）来自事件 M6 融合分。全部来源与公式见 [autoAttackChain.ts](file:///c:/Users/Hobie/Documents/Codex/2026-08-13/github-plugin-github-openai-curated-remote/work/wad-scx/frontend/src/services/autoAttackChain.ts)。
- **M3 事件关联图**：从发现/日志页保存的 30 分钟快照，事件/实体双色节点，实线"涉及"、虚线"先于"、点线"共同参与"。
- **主链/候选/排除三段卡**：每项含标题、摘要、实体归属、操作按钮（加入主链/保留候选/排除）；操作写回 CaseBoard，若案件处于自动观察态会先升级为人工研判。
- **证据时间线表**：按时间排序的 Finding 表，标注当前窗口/历史锚点。
- **实体枢轴**：案件内反复出现的实体统计，可跳转画像。
- **顶部操作**：升级人工案件、分析当前链路、小影（提交案件快照给小影分析）、删除案件。
- **队列状态机**：从 queueStatus/id/owner/status 推断 auto_observe / manual_review / resolved / suppressed / merged 五种状态。
- **为什么**：这是"系统给候选、人来拍板"的核心工作台——不是系统替分析员下结论，而是人机协同做决策，且每个研判动作实时联动总览数字。

**数据来源**：props（cases/findings/caseBoards/m3GraphSnapshots）+ 小影接口 + localStorage 坐标。

### 6.2 上传链路（agent_service/ingestion.py）

核心类 `IngestionStore`，SQLite 持久化到 `run_state/wad_ingestion.db`（WAL 模式），五张 JSON 存储表：jobs / sources / events / windows / investigations。

**处理流程**（文件 → M0-M6 → 持久化）：

1. **解析**：按后缀分派 `.json/.jsonl/.csv/.log/.txt`；`.evtx` 明确报错（需先导出）。
2. **M0**：Drain3 模板挖掘（`safe_mask` 屏蔽 IP/UUID/HEX/数字）→ template_id + parse_confidence。
3. **M1**：语义标准化 + 弱监督规则打分（7 条关键词规则）。
4. **M2**：正则 + payload 字段别名提取实体 → 规则解析器规范化 → 稀有度打分。
5. **M3**：实体图上下文分。
6. **M4**：模板稀有度 + 失败上下文加成。
7. **M5**：与过去最多 100 条风险事件按共享实体关联。
8. **M6**：融合公式输出 final_score；severity 阈值 0.75/0.55/0.35。
9. **落库**：每个事件保存 `module_scores.{M0..M6}`、reasons、raw_log_ref、`labels_used=False`；产出 windows（score≥0.55）与 investigations；job 记录 stage_mean_scores、吞吐、sha256。

### 6.3 小影多智能体编排（agent_service/runtime.py）

基于 OpenAI Agents SDK，**6 个 Agent 协作**：

- `router_agent`：路由决策（security/knowledge/general），带正则兜底（强安全标记直接判 security）。
- `security_agent`：安全分析师，**强制先调用安全工具**再回答，输出 SecurityDraft。
- `knowledge_agent`：知识问答，只挂知识检索工具。
- `general_agent`：普通对话，无内部数据权限。
- `verifier_agent`：证据核验——对 claims 逐条对照证据做支持/不支持/矛盾判定。
- `repair_agent`：把不支持的结论降级改写。

**验证链路**：security 模式且风险分≥80 或置信度<0.75 或命中高风险标记 → 调 verifier；不支持/矛盾时调 repair 收敛，生成 VerificationSummary。**为什么**：防止模型胡编，回答必须可核验。

**工具预算机制**：deep_security 16 次、security 8 次、其余 6 次工具调用上限，防止 agent 失控。

### 6.4 工具层（agent_service/tools.py）

8 个函数工具：`security_get_finding` / `security_search_logs`（limit≤200）/ `security_get_entity` / `security_get_entity_history`（仅 1h/24h/7d）/ `security_get_baseline`（仅 14d/30d/90d）/ `security_get_attack_timeline` / `security_get_investigation` / `knowledge_search`（top_k≤10）。**为什么限定时间范围**：语义上与"多尺度上下文"对应，也防止检索爆炸。

### 6.5 数据仓库抽象（agent_service/repository.py）

`SecurityRepository` 抽象接口 → 三种实现：`JsonDirectoryRepository`（只读适配平台数据包）、`DemoRepository`（仅 mock 模式）、`UnavailableRepository`（未配置时明确失败，但知识检索仍可用）。

`DemoRepository`（`WAD_AGENT_USE_MOCKS=true` 启用）在 mock 模式下额外加载前端 `demo-data/{Short,Long,APT}` 三套数据：把整条时间线纳入事件索引，按 `attack_chain` 步骤与 `final_score≥0.5` 的检测结果生成候选 Finding，使小影在复核链重组候选节点（如 `APT-000010`）时能查到原始证据。同时用 `_extract_entities` 提取攻击者 IP / 后门账户等全部实体，再用 `_merge_entities` 合并前端手工数据与 demo-data 中的同名实体（`svc_backup`、`WEB-01` 等），避免同名实体画像被 `setdefault` 旧画像覆盖。

### 6.6 知识库检索（agent_service/project_knowledge.py）

内置 8 篇项目知识文档（M0-M6 架构、多尺度主动检索、长周期攻击链、跨源语义+实体图、weak_fusion_v2、标签隔离评测协议、TB 级架构、小影工作流）。

`hybrid_lexical_cjk_v1` 混合词法检索：英文词元 + 中文单/双/三字片段（去停用词），打分 = 标题词×4 + 标签词×3 + 内容词 加权词频 × IDF，标题精确包含 +12。**为什么不用向量检索**：无需模型、纯本地、快且可复现，演示稳定。

### 6.7 会话记忆（agent_service/memory.py）

`VisibleConversationStore`：只存用户可见消息（内部工具调用不落库），表 `visible_messages`，最近 30 条。**为什么**：避免把内部推理过程暴露给用户，同时跨页保持会话。

| 要素 | 取值 |
|---|---|
| 攻击者 IP | `45.155.205.233` |
| 主机路径 | `WEB-01` → `DB-01` → `FILE-01`（干扰主机 `FS-02`） |
| 关键账户 | `webadmin`（被利用）→ `svc_backup`（后门，持久化）→ `backup_admin`（稀有但正常，干扰项） |
| 日志源（6 类） | Suricata（IDS）/ Syslog / auth.log / Windows EVTX / DNS 隧道（dnsteal）/ 网络遥测（metricbeat） |
| 攻击链（10 步） | 扫描 → WebShell → 执行 → 建账户 → 提权 → 爆破 → 横向移动 → PowerShell → DNS 隧道 → 数据渗出 |

- **叙事设计**：主链 10 步事件风险曲线呈"侦察 medium → 攻击深入 high → 凭证访问/渗出 critical"梯度；20 条卫星事件分别充当干扰项素材（共享实体但不在链内）、独立低危噪声（自动处置素材）、以及错误案例（`backup_admin` 非工作时间访问 `FS-02` 但存在已批准维护工单 → 应人工排除，呼应"稀有 ≠ 恶意"）。

- **演示前处理**：APT 基准链（`APT-CANDIDATE-001`）默认"提前补全到只剩最后一步（数据渗出）"，现场只需把最后 1 个候选节点拖入主链即可补全 10 步链，避免逐个补全浪费时间。

### 7.4 M6 重投影（project_m6.py）

- **做了什么**：对 timeline.json 每个事件，按与上传链路**同一套口径**计算 M0-M6：
  - M2 = 文件内稀有度 × **基线常见性惩罚**（真实日志中高频实体降权：`0.5 + 0.5/(1+log10(freq+1))`）
  - M4 = 文件内模板稀有度 × 基线模板常见性惩罚
  - M5 = 共享实体的较早风险事件（时间序）
  - M6 = 同一融合公式
- **产物**：`module_scores.json`（每个 event_id 的 M0-M6）+ `outputs/m6_calibration/projection_meta.json`（口径元数据：`labels_used=false`、`synthetic_scores=true`）。
- **为什么**：演示回放与实时上传用同一算法，分数有真实日志统计标定，不读标签。

### 7.5 数据多样性增强（diversify_demo.py，方案 C）

背景：demo 由有限模板重复生成，实体多为高频常见实体，导致顶部分数大量同分（0.6375），区分度差。两个数据层增强：

1. **窗口事件多样性**：对约 60% 的窗口事件（score≥0.5、非链上）做确定性实体替换（注入 svc_backup/deploy/bastion/db-02 等**稀有实体池**），同步改写 related_entities——让 M2 稀有度与 M4 模板指纹出现梯度。
2. **高信号事件注入**：注入 8 族真实风格高信号事件（mimikatz/lsass、certutil、useradd、SSH 爆破、sudo 提权、WAF 告警、PowerShell -enc、auditd），命中上传链路同一套弱监督规则（M1=0.88~0.64），注入事件**共享攻击者实体**使 M5 长程关联自然累积。

- **确定性**：全部基于 event_id 的 FNV-1a 哈希选择，可重复执行。
- **隔离纪律**：链上事件（attack_chain 的 evidence_event_ids）一律不改写；不读任何标签。
- **效果**：顶部分数从 ~0.64 抬到 ~0.71-0.81 并拉开梯度；`SHORT-DIV-*` 注入事件用全大写前缀确保前端案件分类匹配。
- **必须重跑**：之后重跑 `project_m6.py` 重算 module_scores。

### 7.6 跨源真实样本注入（inject_cross_source.py）

### 8.1 标签隔离纪律（全项目铁律）

- 检测/上传链路全程 `labels_used=false`；
- 扫描排除 labels/、labels.csv、EVTX_Tactic 列、ATT&CK 元数据；

**为什么**：这是竞赛最容易被挑刺的"标签泄漏"问题。把隔离纪律写进元数据、让每个产物自证清白，是答辩的底气。

### 8.2 AIT 协议状态机

```
DEVELOPMENT → SOURCE_FROZEN → RELEASE_LOCKED → TARGET_INFERENCE_STARTED
            → PREDICTIONS_SEALED → LABEL_SCORING_ALLOWED
```

`TargetAccessGuard.assert_unlabeled` 拒绝 label/ground_truth/attack_stage 等字段进入检测特征；`prediction_sealer` 对预测文件做 sha256 密封。

## 十二、评委问答（FAQ）

> 以下问答覆盖演示中最可能被追问的点，口径与正文保持一致。回答以"技术事实 + 诚实边界"为原则，先给结论，再给一句可展开的依据。

### 12.1 关于方法创新

**Q1：你们的核心创新到底是什么？和现有 SIEM / SOAR 有什么本质区别？**

答：我们把价值点收敛为三件事——**跨源语义统一**（Syslog/EVTX/WAF/DNS 各说各话，先统一到同一事件语义与实体空间再关联）、**多尺度上下文主动检索**（以当前事件为锚点，1h/24h/7d/30d 按需扩展，而非等量扫全量）、**长周期攻击链关联**（用稳定实体锚点连接跨日窗口，恢复短窗口看不到的完整链）。区别于 SIEM 的"告警罗列"和 SOAR 的"流程编排"，我们的落点是**把海量日志收敛成少量可解释、可追溯、可执行的人工研判**——每一步都能回溯到原始日志和分层分数。

**Q2：M0-M6 这七层是不是为了凑数？每层真的都必要吗？**

答：不是。M0（解析）→ M1（语义）→ M2（实体）→ M3（图）→ M4（模板稀有）→ M5（长程关联）→ M6（融合）是一条"从原始字节到风险决策"的**单向可解释链路**，每一层产出都能被下一层消费、也能被 UI 单独展示。评委问"这分数怎么来的"，我们能从 M6 一路拆到 M0 的原始日志。

**Q3：M6 融合的权重（0.30/0.12/0.14/0.28/0.16）是拍脑袋定的吗？**

答：权重体现了信号的可信度排序——M1 弱监督规则（0.30）和 M4 模板稀有度（0.28）最直接刻画"像不像攻击"，权重最高；M2/M3/M5 是实体与上下文辅助。关键点不是权重本身，而是**回放数据与实时上传链路用同一套公式和规则**，避免两套算法不一致。我们不做黑盒，每个分数都可点开看依据。

**Q4：为什么要用弱监督而不是强监督？你们有标注数据吗？**

答：真实安全场景缺乏大规模干净标注，用少量高置信关键词规则（如 mimikatz、lsass 必然可疑）即可获得有区分度的先验，且**天然可解释**。我们用四源约 2.2 亿行真实日志做频率标定（哪些实体/模板常见、哪些罕见），而不是用标签训练分类器。

### 12.2 关于数据与标签隔离

**Q5：你们的评测结果是真实跑出来的吗？会不会标签泄漏？**

答：评测指标（PR-AUC 87.0%、Recall@1%FPR 81.0%、3-day Chain Recovery 72.6%）是基于真实实验的演示静态值，我们**不宣称是正式竞赛的最终评测结果**。标签隔离是全项目铁律：检测链路全程 `labels_used=false`，扫描排除 labels/ 与 EVTX_Tactic 列，系统先独立生成预测、**结果落盘后**评测程序才读标签（`PREDICTIONS_SEALED → LABEL_SCORING_ALLOWED` 状态机）。

**Q6：demo 里的攻击链是不是你们手工编的？这样能说明检测能力吗？**

答：演示回放数据（Short/Long/APT）是**为演示设计的受控事件流**，`manifest.json` 明确 `model_execution=false`、`synthetic_scores=true`、`contains_labels=false`——我们把它当作"素材库"来验证交互和调查闭环，而不是宣称它是模型在真实数据上的检测结果。真实的检测能力由四源真实日志的统计标定 + 小文件真实上传链路 + 独立标签评测来支撑。这条边界我们在 UI 和答辩里都主动声明。

**Q7：APT 数据集里的攻击者是真实攻击吗？**

答：不是。`APT` 数据集是专为 10 分钟演示剧本设计的**叙事集**（`scripts/build_apt_demo.py` 确定性生成），攻击者 IP `45.155.205.233`、后门账户 `svc_backup` 等都是构造的叙事要素，分数由与上传链路一致的 M6 公式合成，不读标签。它解决的是"用一条逻辑自洽的故事串起每个功能"，而非声称这是真实 APT 案例。

### 12.3 关于可解释性与"稀有 ≠ 恶意"

**Q8：风险分数高就一定代表攻击吗？你们怎么处理误报？**

答：不。我们反复强调**稀有 ≠ 恶意**。典型错误案例：`backup_admin` 非工作时间访问文件服务器确实异常，但存在已批准维护工单时，就应由人工排除。系统解释误报来源，而不是把稀有直接当成恶意。UI 上每个发现都有三层分数 + 关联理由 + 原始日志引用，分析员能判断"这是真攻击还是稀有但正常"。

**Q9：链罕见度 73% 是怎么算的？可靠吗？**

答：`链罕见度 = 35%·M2实体稀有 + 30%·M4模板稀有 + 20%·时间压缩度 + 15%·高风险占比`。其中 M2/M4（占 65%）是**真实数据标定**——基于四源 2.2 亿行真实日志的频率统计（高频实体/模板降权）；时间压缩度是可解释的领域启发式（短时间走完整条链更异常，公式透明可复现）。它定位为"调查信号"，UI 挂了边界声明，不是入侵结论。

### 12.4 关于系统架构与规模

**Q10：你们能处理 TB 级日志吗？吞吐是多少？**

答：**当前版本不把吞吐外推为 TB 实测结论**。原型已跑通小文件真实上传 + 完整 M0-M6 + SQLite 持久化，测的是小样本功能正确性（EPS 15,435 为演示口径）。TB 级要走 Collector + Kafka + Flink 的分区架构，这个口径我们很克制，文档和评测页都明确标注 `formal_evaluation=False`。

**Q11：为什么前后端要分"回放层"和"实时接入层"两条数据路径？**

答：回放层（Short/Long/APT）保证演示任何时间、任何网络都可用，且完整保留"原始日志 → 结论"的可追溯性；实时接入层（小文件上传 → FastAPI → M0-M6 → SQLite）证明系统不是前端假数据。两条路径用**同一套 M6 公式和规则**，避免两套算法不一致。

### 12.5 关于智能体"小影"

**Q12：小影不就是套壳 LLM 吗？**

答：模型是**可替换的推理层**，但项目知识、检测工具、上下文和证据协议都是我们自己提供的。小影的回答必须引用内部工具证据（`security_get_finding` 等 8 个工具），且走"security_agent 生成 → verifier 核验 → repair 降级"的编排，防止模型胡编。它还带可执行按钮，点一下跳转对应案件/实体/日志，形成人机协同闭环。

**Q13：小影会不会把内部推理过程泄露给用户？**

答：不会。会话记忆只存用户可见消息（`visible_messages`），内部工具调用不落库；API Key 只存进程内存、重启即失效。这既是隐私边界，也是演示安全的考虑。

### 12.6 关于工程与工程能力

**Q14：这个系统里有多少是真实代码，多少是前端假数据？**

答：检测与上传链路（M0-M6、SQLite、实体图、长程关联）是**真实可运行的后端代码**；前端回放数据是"受控演示事件流"用于展示交互，但小文件上传会走后端真实链路。两者边界清晰：`manifest.json` 的 `model_execution` / `synthetic_scores` 字段自证。

**Q15：为什么选择 React + FastAPI + OpenAI Agents SDK 这套技术栈？**

答：前端 React 生态成熟、Ant Design 组件齐全、ECharts 适合关系图；后端 FastAPI 轻量、异步原生、适合做 SSE 流式；OpenAI Agents SDK 提供多智能体编排、工具调用和 token 预算，让我们能聚焦在"调查副驾"的编排逻辑而非底层协议。
